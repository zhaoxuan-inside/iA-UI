# iA-UI 产品设计书 v0.0.3 评审报告

本次评审以你上传的《iA-UI 产品设计书（v0.0.3 · AI 驱动原生版）》为主要依据，围绕三个维度展开：完整性、兼容性、创新性。重点不是评价文档写得是否丰富，而是判断它能否形成一个边界清晰、可以落地实施、能够融入现有开发生态并具有竞争壁垒的产品。

## 一、总体评价

评分为基于产品设计文档的分析性判断，不是市场调研结果、用户测试结论或实际系统测试成绩。

我的核心判断是：这份设计书已经超越了单纯的“自然语言生成 UI”工具构想，开始定义一种供外部 Agent 调用、以结构化 UI 规格为核心的设计基础设施。 这是最值得保留的产品方向。

但目前文档主要回答了“产品应该具备哪些能力”，还没有充分回答以下问题：

- 各项能力之间如何通过明确的数据契约形成可运行的闭环？
- 面对真实的前端项目、设计文件和不同 MCP 客户端，如何保证兼容性？
- 哪些创新能真正转化为竞争壁垒，而不只是现有技术的组合？
- 当多人、多个 Agent 并发修改同一份设计时，如何保证一致性、安全性与可恢复性？
- 如何用客观指标证明交付的 UI 规格确实能够指导代码开发？

下面逐项分析。

## 二、完整性分析：设计域覆盖广，但端到端产品闭环尚未完全定义

### 2.1 已经设计得比较完整的部分

这份设计书最突出的优点，是没有停留在生成页面，而是覆盖了从需求到工程交付的多个关键阶段。

## 现有产品能力链

需求输入与 PRD

自然语言、草图、截图、既有设计

语义设计与组件装配

意图、约束、布局、图元、设计令牌

可视化工作台与原型

直接编辑、局部重生成、交互演示、多终端适配

规格交付与实现验证

UI Spec、设计说明、标注图、演示视频、代码视觉验证

以上链路是对设计书第 3—8 章能力的归纳，并非文档已经证明可以完整运行的流程。

尤其值得肯定的是以下五点。

| 评审项目    | 文档中的设计                 | 评价              |
| ------- | ---------------------- | --------------- |
| 需求与设计关联 | PRD 与画板双向绑定            | 有利于减少需求和设计脱节    |
| 设计表达    | 四层语义模型、稳定语义 ID、流式布局    | 为机器读取与增量修改提供基础  |
| 人机协作    | Scope Guard、方案确认、局部干预  | 重视可控性，而非只追求自动生成 |
| 工程交付    | UI Spec、组件映射、Mock、状态枚举 | 比单纯导出图片更接近研发工作流 |
| 版本与验证   | 快照、Diff、回滚、视觉与规范检查     | 具备闭环设计意识        |

这些能力分别见设计书第 3—7 章。

### 2.2 完整性缺口：从“功能清单”到“可执行产品”

完整性并不等于功能数量多。真正关键的是每项功能有没有明确的输入、处理规则、输出、失败处理和验收条件。

问题 1：核心数据模型没有形成完整的规范定义

文档提出了 JSON UI Spec、稳定语义 ID、PRD 与画板绑定、组件映射，但没有在产品设计层完整定义这些对象的字段、引用关系、生命周期及约束。

例如：组件被删除后，PRD 引用、交互动作、跨端衍生画板和历史版本如何处理？同一个组件的视觉属性与业务语义分别由谁维护？

建议： 补充核心实体及关系规范，至少覆盖 Project、Page、Node、Component、Token、Interaction、Mock、PRD、Version、Asset 和 ValidationReport。

问题 2：双向编辑的冲突规则不完整

文档定义了 DSL → 画布、画布 → DSL 的双向映射，也提出版本快照与局部补丁，但没有完整说明并发修改的冲突解决机制。

例如：设计师修改按钮间距时，外部 Agent 同时修改了按钮父容器布局；两个修改是否可以合并？如果不能，谁来裁决？

建议： 定义基于版本前置条件的补丁提交、冲突检测、字段级合并、冲突预览和显式回滚规则。

问题 3：权限模型有层级，但缺少操作安全契约

文档定义了组织、项目、页面、节点和资源等权限粒度，也规定外部 Agent 以受限身份运行。

但还需要明确：授权如何撤销、凭证过期如何处理、批量操作如何限界、删除和发布是否需要二次审批，以及如何防止恶意设计文件或外部 Agent 输入诱导越权操作。

建议： 把授权范围、操作类型、资源范围、有效期、审批条件、审计记录和撤销行为纳入完整的权限设计。

问题 4：验收标准还没有可测量化

文档提出设计效率提升、代码还原度高、一次通过率高、返工率低等目标，但没有给出测量方法和达标阈值。

建议： 规定测试基准、样本集、指标口径和目标值，例如规格校验通过率、视觉差异、交互覆盖率、人工修复时间及回归缺陷率。

问题 5：协作与发布生命周期定义不足

文档有角色权限、版本快照、设计市场和资产上架，但对多人协作中的评论解决、审批状态、发布冻结、版本依赖、团队资产更新和下架后的存量使用规则说明不够。

建议： 明确草稿、评审、批准、发布、废弃等生命周期状态，并定义版本依赖和兼容性迁移规则。

### 2.3 特别需要注意：产品的“智能外置”与“设计闭环”之间存在张力

设计书明确规定产品不内置 Agent、不负责 LLM 推理、不承担 Agent 编排，所有智能通过外部 Agent 提供；同时又要求实现模糊意图澄清、自动生成、局部修复、跨端衍生以及验证后自愈。

Pasted markdown.md



这两项原则并不矛盾，但需要明确分工：

- 外部 Agent 负责推理与决策：理解用户意图、规划任务、选择设计方案、根据诊断决定如何修复。
- iA-UI 负责确定性执行：解析和校验规格、渲染画布、执行受限补丁、检测冲突、记录版本、输出验证结果。
- 双方通过协议完成闭环：产品返回结构化结果和错误码，Agent 根据结果决定下一步操作。

例如，“让结算页更有质感”属于外部 Agent 的理解和方案生成任务；“间距必须为 16px”“只能修改结算卡片子树”则应当由产品自身的确定性规则执行。

如果产品内部没有定义好这些确定性能力，外部 Agent 就会承担过多的隐性逻辑，最终形成一个依赖特定 Agent 才能正常工作的工具，而不是通用的设计引擎。

完整性结论： 设计域的功能覆盖比较全面，但数据契约、冲突治理、操作安全和验收标准需要进一步补齐。当前更接近完整的产品蓝图，还不能仅凭文档认定为完整的实施规格。

## 三、兼容性分析：架构方向开放，但“支持标准”不等于“互操作成功”

我把兼容性拆成五个维度：协议、数据格式、前端组件、设计文件、运行环境。

| 兼容性维度       | 当前设计                                      | 主要风险                   | 判断       |
| ----------- | ----------------------------------------- | ---------------------- | -------- |
| 外部 Agent 接入 | MCP 标准接口                                  | 不同客户端的工具发现、调用和授权行为可能不同 | 方向正确，需验证 |
| UI 规格       | JSON UI Spec、稳定 ID、JSON Schema            | 自定义语义尚未定义为完整的公开契约      | 中等风险     |
| 设计令牌        | DTCG                                      | 需明确采用的规范版本及扩展规则        | 基础较好     |
| 前端组件        | React、Vue、Svelte 等；shadcn/ui、Ant Design 等 | 组件属性、插槽、主题、事件语义差异      | 高风险      |
| 设计文件        | Figma `.fig`、截图、草图                        | 转换损失、复杂节点和效果的表达差异      | 高风险      |

### 3.1 MCP 兼容性：协议统一，不代表调用能力完全一致

文档希望任意 MCP 兼容 Agent 都能连接产品。这是合理的开放策略，但需要把“支持 MCP”进一步定义为可以互操作的产品契约。

建议明确：

1. 协议版本与能力发现：产品支持哪些 MCP 协议版本、工具发现方式及调用行为。
2. 工具输入输出契约：每个工具的参数 Schema、返回结构、错误码、分页与超时行为。
3. 授权与隔离：项目级、页面级、节点级权限如何传递和校验。
4. 长任务处理：大规模设计生成、批量导入、验证任务如何查询进度和恢复。
5. 兼容性测试：用多个实际 MCP 客户端进行读、写、校验、失败重试和权限越界测试。

尤其重要的是，MCP 只负责约定交互协议，并不会自动统一不同 Agent 的推理能力、上下文管理和错误恢复策略。

因此，不能仅凭 MCP 接口开放就宣称“任意 MCP Agent 均可完整使用全部能力”。

### 3.2 DTCG 兼容性：应采用标准格式，而不是只借用术语

设计书以 W3C DTCG 为设计令牌基础，这是一个正确的选择。

外部资料显示，DTCG 在 2025 年 10 月发布了稳定版 2025.10 格式规范，目标正是让设计令牌在不同设计工具、代码库和平台之间交换。

[image](https://www.google.com/s2/favicons?domain=https://www.w3.org\&sz=32)

W3C

+1



但这里仍然有一个重要区别：

- 采用 DTCG：令牌数据遵循标准的类型、值、别名和分组约定。
- 兼容 DTCG：不仅能够导入导出，还能正确处理主题、别名、复合令牌、颜色空间以及未知扩展。
- 真正互操作：导入、修改、再导出后，语义和目标平台的实际视觉效果仍能保持一致。

文档中“严禁裸色值”适合作为设计治理规则，但应区分内部规范和外部导入数据：外部项目可能存在合法的字面量颜色，导入时应该先检测、归一化或报告，而不是直接拒绝整个项目。

建议： 采用标准 DTCG 格式作为交换层，内部可以有更丰富的设计模型，但必须定义可预测的映射、降级和往返转换规则。

### 3.3 前端组件兼容性：这是最容易低估的工程难题

文档提出将设计组件映射到真实工程组件库，支持 React、Vue 3、Svelte 等技术栈，并导入 Storybook 元数据或 TypeScript Props。

Pasted markdown.md



方向正确，但组件不能只按名字和外观映射。

以一个按钮为例，不同组件库可能具有不同的：

- 属性名称、默认值、枚举值及互斥约束；
- 事件签名和异步行为；
- 子元素、插槽和复合组件组织方式；
- 加载、禁用、危险操作等状态；
- CSS 变量、主题上下文和样式覆盖机制。

即使两个组件都叫 `Button`，也不意味着它们能够一一映射。

我建议增加一个组件适配器契约：

| 契约字段      | 用途                |
| --------- | ----------------- |
| 组件身份      | 来源库、版本、导出路径、唯一标识  |
| 属性 Schema | 类型、默认值、枚举、必填和互斥规则 |
| 插槽与子组件    | 定义组合方式与层级约束       |
| 事件与动作映射   | 将设计原型动作映射到目标框架    |
| 主题映射      | 令牌、CSS 变量和样式依赖    |
| 能力与限制     | 支持的状态、交互、布局及已知缺陷  |
| 版本兼容策略    | 升级、弃用、迁移和替代组件规则   |

这能避免产品只生成“看起来像 Ant Design”的 UI，却无法在真实项目中稳定运行。

### 3.4 Figma 导入：必须将“可导入”与“无损转换”区分开

文档将 `.fig` 导入和 AI 语义重构列为能力，但没有定义导入的保真等级与支持边界。

这不是小问题。OpenPencil 的文件格式说明也明确提示：复杂 Figma 文档在往返转换时可能出现组件内容、颜色和文本等视觉差异。OpenPencil 的相关说明可作为实际风险参考。

[image](https://www.google.com/s2/favicons?domain=https://openpencil.dev\&sz=32)

OpenPencil



因此，建议将导入能力划分为三个等级：

L1

结构保留

尽量保留页面、图层、文本、图片和基础矢量结构；无法解析的对象保留为原始资产。

L2

语义重构

将可识别的布局转换为流式盒模型，识别组件与令牌，记录无法自动转换的节点。

L3

工程映射

将重构后的组件、样式和交互映射到目标前端工程，并验证渲染差异。

每次导入都应生成转换报告，说明保留、转换、降级、丢失的内容，并允许用户定位到具体节点。

### 3.5 兼容性结论

iA-UI 的开放架构是兼容性优势，但目前开放更多体现在设计理念和接口方向，而不是已经定义完整的互操作契约。

优先补齐顺序应当是：

1. UI Spec 版本化与兼容规则；
2. MCP 工具契约与客户端兼容测试；
3. 前端组件适配器；
4. DTCG 导入导出及主题映射；
5. Figma 转换保真度与降级报告。

## 四、创新性分析：创新主要来自架构组合，而不是单个功能

我认为这份设计书最值得关注的创新，是把 UI 设计工具从“人类操作的图形编辑器”转向“外部 Agent 可以调用的结构化设计引擎”。

不过，创新性需要分成三个层面判断：理念创新、产品机制创新、可形成壁垒的创新。

创新点 1：设计能力外置为 Agent 可调用的引擎

高潜力

文档将 Agent 与设计平台解耦，通过 MCP 暴露规格读取、写入、生成、校验和版本管理能力。

价值： 同一个设计引擎理论上可以被不同编码 Agent、研发工作流和自动化工具复用，降低平台对单一模型或 Agent 产品的依赖。

判断： 架构定位有差异化潜力，但 MCP 本身不是创新。真正的差异在于设计能力是否足够专业、稳定、可组合。

创新点 2：面向 AI 的确定性语义设计语言

高潜力

以意图、约束、布局、图元四层模型组织设计数据，并结合稳定语义 ID、明确尺寸策略和双向映射。

价值： 将传统设计中大量隐含在画布和图层关系里的信息，转化为可以检索、修改、校验和版本比较的数据。

判断： 这是最有可能成为产品核心技术资产的部分。前提是它不仅能表达页面，还能可靠地表达组件关系、交互、状态和跨端约束。

创新点 3：Scope Guard 与局部补丁机制

机制创新

把人类划定的编辑范围变成执行约束，外部 Agent 的修改越界时直接拒绝。

价值： 将“AI 尽量不要改坏其他部分”转化为可以验证的产品规则。

判断： 比单纯的提示词约束更可靠。但它需要与版本前置条件、依赖检查、并发冲突检测和原子提交结合，否则仍可能发生间接影响。

创新点 4：从设计规格到代码验证的闭环

高价值

通过受控浏览器渲染、视觉比对和规范检查，将诊断结果反馈给外部编码 Agent。

价值： 产品不只是交付设计，还能帮助判断设计在真实实现中是否被正确还原。

判断： 这是非常有商业价值的方向，但视觉比对、浏览器自动化和组件测试本身已有成熟实践。差异化在于设计规格、实现结果和诊断修复之间能否建立可靠关联。

创新点 5：生产级设计资产市场

待验证

市场售卖的不只是设计图片，还包括 UI 规格、交互动作和代码约束。

价值： 有机会让设计资产直接进入开发流程，降低重复设计和实现成本。

判断： 商业模式有吸引力，但市场、授权、交易、防爬虫等能力并非技术创新本身。其成立依赖资产质量、真实使用率、生态规模和版权治理。

### 4.2 哪些是已有能力，哪些是组合创新？

需要避免把已有标准和开源项目的能力直接当成产品自身的原创技术。

| 设计能力   | 现有基础                          | iA-UI 应形成的增量                |
| ------ | ----------------------------- | --------------------------- |
| 设计令牌   | DTCG、Style Dictionary         | 将令牌与语义画布、组件及验证统一起来          |
| 自动布局   | Figma Auto Layout、CSS Flexbox | 为 Agent 提供确定性的布局约束和可修改的数据模型 |
| 组件元数据  | Storybook、各类组件库               | 统一跨库组件映射和工程可落地性             |
| MCP 调用 | MCP 生态                        | 将设计操作封装成可组合、受控、可审计的能力       |
| 视觉回归   | Playwright、Storybook 等工具      | 把设计规格与实现差异关联，并生成可执行诊断       |
| 版本管理   | Git、协同编辑系统等                   | 提供语义级设计 Diff、局部补丁和安全合并      |

例如，DTCG 的价值在于跨工具交换设计令牌；它本身并不提供完整的 UI 语义设计引擎。

### 4.3 最有可能形成技术壁垒的三个方向

第一优先级：统一语义模型与可靠增量修改

建立设计数据模型、稳定 ID、约束关系、补丁语义、版本兼容和冲突处理规则。这决定平台能否成为外部 Agent 长期依赖的设计基础设施。

第二优先级：设计规格与真实代码之间的验证能力

不仅比较截图，还要判断组件、令牌、布局、交互和状态是否符合设计契约，并将缺陷定位到具体语义节点。

第三优先级：跨技术栈组件适配体系

将不同框架和组件库统一映射到共同的设计语义，再通过适配器转换到具体工程。随着经过验证的组件映射和兼容性用例积累，迁移成本才可能成为壁垒。

## 五、产品设计中最需要修正的几个问题

以上三个维度综合来看，我认为以下问题应当优先修改。

| 优先级 | 问题               | 影响                 | 建议的修正方向                   |
| --- | ---------------- | ------------------ | ------------------------- |
| P0  | UI Spec 的正式契约不完整 | Agent 无法稳定生成和修改设计  | 定义版本化 Schema、实体关系、补丁和错误语义 |
| P0  | 设计修改缺少完整冲突治理     | 并发编辑可能丢失修改或破坏依赖    | 引入版本前置条件、冲突检测和原子提交        |
| P0  | 组件映射没有完整契约       | 设计能生成，但无法可靠映射到真实工程 | 建立组件适配器和兼容性测试             |
| P0  | 验收指标没有明确阈值       | 无法证明产品效果，也无法回归测试   | 定义基准数据集、指标口径与通过标准         |
| P1  | MCP 接口与客户端兼容性未量化 | “开放接入”可能停留在理论层面    | 定义协议版本、工具契约和客户端测试矩阵       |
| P1  | Figma 导入保真边界不明确  | 用户可能遭遇不可预期的设计损失    | 建立保真等级、转换报告和失败回退          |
| P1  | 团队协作及发布生命周期不足    | 难以支撑企业设计流程         | 增加审批、发布冻结、依赖版本和资产治理       |
| P2  | 设计市场过早纳入核心范围     | 分散核心引擎的研发资源        | 将市场放到核心工作流验证之后            |

这里的 P0/P1/P2 是本次评审提出的整改优先级，并非原文已有定义。

## 六、建议如何重构产品实施路线

不建议按文档现有章节的顺序直接开发，也不建议一开始就实现所有功能。更合理的路线是先证明核心设计引擎可以稳定工作，再扩展生态。

## 01

### 第一阶段：建立最小语义设计引擎

最高优先级

- 定义 UI Spec、语义 ID、组件、令牌、布局与交互数据模型。
- 实现 JSON 校验、画布渲染、局部补丁、撤销与快照。
- 提供 MCP 读写接口和最基本的授权范围控制。
- 选择一个前端技术栈和一套组件库进行验证。

验收目标： 外部 Agent 能通过标准接口生成页面、修改局部区域，设计师可以检查和撤销，且无效修改不会破坏原有设计。

## 02

### 第二阶段：证明设计可落地

- 建立真实组件映射与设计令牌导出。
- 完成页面状态、Mock 和交互原型。
- 对生成代码进行浏览器渲染、视觉对比和规范验证。
- 形成结构化诊断报告，并让外部 Agent 根据报告修复。

验收目标： 同一份设计规格可以被目标工程稳定消费，并能够定位实现偏差，而不是只交付一张视觉相似的图片。

## 03

### 第三阶段：扩大兼容范围

- 支持更多 MCP 客户端、前端框架与组件库。
- 增加 Figma 导入、语义重构和跨端衍生。
- 建立多人协作、并发冲突处理和团队设计系统治理。

验收目标： 增加一种客户端或目标技术栈时，不需要重写核心语义模型。

## 04

### 第四阶段：生态和商业化

- 建立资产发布、版本依赖、授权和更新机制。
- 支持团队资产包复用和市场交易。
- 根据真实使用数据验证资产复用率与商业价值。

验收目标： 设计资产不仅能展示和售卖，还能被目标工程真实使用、升级和维护。

## 七、最终结论

### 完整性：较强，但还不是可直接实施的完整规格

文档已经覆盖需求、设计、工作台、组件、交付、验证和市场等主要领域。最大的缺口是数据模型、操作契约、冲突治理、安全边界及可量化验收标准。

### 兼容性：架构开放，实际互操作能力尚待证明

MCP、DTCG 和真实组件映射为开放生态奠定了基础，但不能只依靠标准名称来保证兼容。需要建立 UI Spec 版本管理、组件适配器、文件转换报告和自动化兼容性测试。

### 创新性：值得继续推进，但应集中在核心引擎

最有价值的方向是把设计转化为外部 Agent 可以可靠读写、可局部修改、可验证并可交付开发的结构化资产。单独的 MCP 接入、设计市场或 AI 生成并不足以构成长期壁垒。

我的最终建议是：保留 v0.0.3 的核心产品定位，但下一版不要继续优先扩充功能清单。

应该优先补齐三份基础设计：

1. 《iA-UI 语义设计数据模型与 UI Spec 规范》：定义数据结构、版本兼容、稳定 ID、组件映射、交互状态及增量补丁规则。
2. 《iA-UI MCP 能力契约与安全规范》：定义每个工具的输入输出、权限范围、失败语义、审计和客户端兼容要求。
3. 《iA-UI 端到端验收与兼容性测试规范》：定义如何证明设计能够被真实前端工程消费、如何量化视觉和交互差异，以及如何验证局部修改不会破坏其他部分。

这三项基础工作完成后，再实现设计市场、多框架支持和完整的资产生态，会更容易控制复杂度。

最终判断：产品方向值得继续推进。现阶段的关键不是增加更多 AI 功能，而是把“AI 能够生成 UI”提升为“不同 Agent 都能可靠操作、修改、验证和交付 UI”。 这才是这份产品设计书最有潜力建立差异化的地方。
