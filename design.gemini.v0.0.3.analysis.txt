# iA-UI v0.0.3 产品设计完整性、兼容性与创新性评审

## 一、总体评价

这份《iA-UI 产品功能与体验设计说明书 v0.0.3》设计的是一个 AI 原生的 UI 设计工作台：用户通过自然语言、PRD 和品牌约束表达需求，由多个 Agent 协同生成页面、布局、设计系统和交互原型，再通过结构化 UI Spec 将设计交付给编码 Agent，最后利用自动化验证形成闭环。

design.gemini.v0.0.3.md



我的核心判断是：产品理念比较先进，功能覆盖面较广，核心技术方向基本合理，但目前更接近一份完整的产品愿景与系统功能蓝图，还不能视为已经解决关键工程问题的可实施产品规格。

这份设计最有价值的地方，不是简单地将 AI 聊天框嵌入设计工具，而是试图建立从业务意图、设计语义到生产代码的统一模型，并让设计修改能够反向影响结构化规格。

与此同时，文档也存在一个关键问题：它对理想状态描述得非常完整，但对于如何在真实项目中保证生成正确性、兼容性、修改可控性和交付质量，仍有一些重要环节没有定义。

## 评审结论

完整性：较高，但闭环尚不完整

业务流程、核心模块、领域实体、异常处理已有较广覆盖，缺少若干跨模块契约与实施细节。

兼容性：方向正确，互操作性尚未证明

重视标准、组件注册和多端布局，但导入导出、DSL 语义映射和跨工具一致性仍有风险。

创新性：架构理念有辨识度，单项技术多为成熟能力的组合

主要创新在于语义统一、双向修改、作用域保护和生产验证闭环的整合，而不是每项底层技术本身。

以下分析以原文为依据。涉及设计缺陷、工程风险和改进建议的部分，是基于产品设计及软件架构原则作出的评审推断，不代表文档已经实现了相应能力。

## 二、完整性分析

完整性不能只看功能数量，还要看从用户输入到最终交付的业务链条是否完整、每个模块之间是否存在明确契约，以及异常情况下是否仍能正确运行。

### 2.1 核心业务链条完整性

文档设计了四个主要阶段：意图推演、自主合成、人机精修、双向交付与生产验证。整体流程是合理的。

design.gemini.v0.0.3.md



1\. 需求输入与业务推演

自然语言 / PRD / 品牌规范 → 业务实体、页面拓扑、验收标准

2\. AI 自主设计与装配

Token、组件、布局、响应式画板、交互原型、Mock 数据

3\. 人机协同修改

画布直接操控、自然语言修改、作用域保护、版本快照

4\. 工程交付与自动验证

UI Spec → 编码 Agent → 实际渲染 → 差异诊断 → 修复

验证结果应能够反向更新任务状态、诊断记录和后续修复流程

说明：该图是对文档已有流程的归纳，不表示所有反馈和状态转换已经被完整定义。

这条主链条覆盖了多数 AI UI 设计工具容易忽略的阶段，特别是结构化交付与生产代码验证。

但有五个明显缺口。

### 2.2 完整性缺口清单

以下优先级是根据对产品核心价值的影响进行的评审判断，并非文档自身给出的等级。

| 优先级 | 缺失或不足的能力      | 具体问题与影响                                                           |
| --- | ------------- | ----------------------------------------------------------------- |
| P0  | 统一 UI Spec 契约 | 定义了 JSON Schema 方向，但没有给出完整的规范版本、字段约束、语义规则和兼容策略。各模块可能对同一份规格产生不同理解。 |
| P0  | 生成结果的正确性标准    | 有验证指标和视觉差异检查，但缺少完整的验收判定规则、阈值、误报处理及无法修复时的退出条件。                     |
| P0  | 变更与冲突管理       | 定义了 Scope Guard 和人工优先原则，但没有充分说明并发修改、过期补丁、跨节点依赖、撤销与重做的统一语义。        |
| P1  | 用户需求与设计追踪     | PRD、验收规则、页面和节点已经建立部分关联，但缺少从每项需求到页面、交互、测试及交付结果的完整追踪机制。             |
| P1  | 真实业务逻辑与数据契约   | 目前重点是视觉 Mock 和轻量交互原语，没有充分定义复杂表单校验、业务权限、异步状态和真实 API 契约的交付边界。       |
| P1  | 团队协作与发布治理     | 有 RBAC、快照和评审角色，但协作锁、合并策略、审批流程、环境隔离和发布权限的具体规则不足。                   |
| P1  | 运行成本与性能治理     | 提及 60fps、毫秒级反馈和 Agent 并行，但没有给出大型项目的节点规模目标、延迟预算、Token 消耗预算及降级策略。   |
| P2  | 市场运营完整性       | 已有资产上架、授权和结算方向，但内容审核、退款争议、侵权处理、版本依赖和资产下架后的项目行为尚未说明。               |

这里最重要的是前三项。因为它们直接影响整个产品能否可靠工作，而不仅仅是影响某个外围功能。

### 2.3 五个容易被忽略的深层问题

#### 问题一：UI Spec 是整个产品的核心，但尚未成为可验证的正式契约

文档把 UI Spec 作为 Single Source of Truth，并定义了布局树、Token、交互路由、Mock 数据等内容。

design.gemini.v0.0.3.md



这个方向正确，但“使用 JSON Schema”不等于“规格已经标准化”。

至少还应定义：

- 结构契约： 页面、节点、组件、动作、数据源各有哪些必填字段。
- 语义契约： `fill` 在不同父容器、滚动容器和断点下究竟如何计算。
- 引用契约： 节点、组件、Token、路由被删除或重命名后，如何处理引用。
- 版本契约： Spec 从 v1 升级到 v2 时，旧项目如何迁移，旧编码 Agent 如何识别新字段。
- 扩展契约： 第三方组件和自定义动作如何扩展，同时不破坏校验。
- 确定性契约： 相同输入在不同渲染器、不同时间和不同运行环境下，应保证哪些属性一致。

如果这部分没有落实，那么五个 Agent 即使各自工作正确，协作结果也可能不一致。

#### 问题二：设计验证与真正的生产验收之间存在差距

文档提出使用无头浏览器、视觉差异、布局溢出、Token 合规性和状态覆盖率进行自动检查，并通过诊断单驱动编码 Agent 自愈。

design.gemini.v0.0.3.md



但视觉一致并不等于产品正确。

例如，一个支付页面可能满足以下条件：

- 布局没有溢出；
- 字体、颜色、间距都符合设计规范；
- 按钮视觉状态正常；
- 页面截图与目标图高度相似。

然而，余额不足时仍然允许提交支付。这是业务逻辑错误，而非视觉错误。

建议将验证体系拆成四层：

L1：规格合法性

Schema、引用完整性、动作参数、Token 和节点 ID 校验。

L2：视觉与布局正确性

溢出、断点、对齐、字体、对比度、截图差异和不同语言下的布局。

L3：交互与业务正确性

状态机、路由、表单校验、异常分支、权限条件及业务验收规则。

L4：工程与生产可交付性

构建、依赖、安全、无障碍、性能、回归测试及部署环境适配。

其中 L3 和 L4 需要补充为明确的产品能力，不能仅凭视觉验证闭环推定已经覆盖。

#### 问题三：Scope Guard 解决了越界修改，但没有完全解决依赖一致性

文档明确提出：修改目标节点时锁定节点树，其他画板只读，并在补丁应用前检查目标节点是否越界。

design.gemini.v0.0.3.md



这能降低 AI 修改无关区域的风险，但考虑以下情况：

设计师修改一个全局 Button 组件的高度，影响了 80 个页面；用户只锁定了当前页面上的一个按钮。

系统需要判断：

- 当前修改究竟是组件实例覆盖，还是主组件定义修改？
- 如果是主组件修改，如何识别全部受影响的页面？
- 哪些变化属于允许的依赖传播，哪些属于越界修改？
- 如果部分页面不兼容，是否允许部分提交？
- 如果用户拒绝同步其他页面，系统如何保留分叉？

因此，作用域控制应区分直接修改范围、依赖传播范围和最终影响范围，而不能只靠节点写锁来解决。

#### 问题四：AI 修改操作需要有事务语义

文档定义了 JSON Patch、稳定语义 ID、版本快照、回滚和人工优先等机制，但没有完整定义它们如何共同工作。

建议每一次 Agent 修改都采用以下流程：

1. 生成补丁并声明预期修改范围。
2. 校验基础版本是否仍然有效。
3. 校验权限、节点引用和依赖约束。
4. 在临时版本中应用补丁。
5. 执行规格与依赖验证。
6. 原子提交，或整体拒绝。
7. 记录变更原因、差异、验证结果和可回滚版本。

这能够避免部分修改成功、部分失败，最终造成设计树处于不一致状态。

#### 问题五：功能完整，不代表用户工作流完整

文档定义了设计总监、产品经理、开发工程师等角色，但实际操作中还需要明确：

- 新用户如何创建第一个可交付项目？
- 用户只想生成一张登录页时，是否必须经过完整 PRD 推演？
- 用户已有 Figma 设计稿时，如何跳过不必要的生成环节？
- 用户只想修改颜色时，如何避免触发整个 Agent 集群？
- 用户对生成结果不满意时，如何比较候选方案并恢复之前版本？
- 用户在项目中途更换组件库时，如何迁移现有资产？

文档已有宏观和微观两种工作流，这是良好基础；但还需要定义不同任务规模、用户熟练程度和项目阶段下的实际入口与完成标准。

### 2.4 完整性最终判断

已经覆盖得比较好的部分

产品主流程、Agent 职责、语义画布、设计系统、Mock、版本快照、异常拦截、权限框架和交付方向。

尚需补齐的部分

统一规格契约、复杂依赖合并、业务测试、生产验收、协作冲突和性能预算。

结论：功能目录层面的完整性较高，工程闭环层面的完整性中等，生产实施规格的完整性仍不足。 这是基于文档内容的定性评估，而非对已运行产品的实测评分。

## 三、兼容性分析

这里将兼容性拆成六类：设计资产兼容、前端组件兼容、跨端兼容、编码 Agent 兼容、标准协议兼容，以及版本兼容。

### 3.1 设计资产与生态兼容性

文档计划支持 Figma `.fig` 导入、截图逆向推导、Storybook 组件元数据、多个主流组件库，以及自定义字体与图标。

design.gemini.v0.0.3.md



这是合理的生态策略，但“支持导入”至少有三个不同层级：

| 层级      | 含义                         | 文档当前状态         |
| ------- | -------------------------- | -------------- |
| L1：读取   | 能够提取资产、文本、组件、布局和样式         | 已提出目标          |
| L2：语义转换 | 能够将资产转换成可编辑、可约束的统一 UI Spec | 已提出转换方向，具体规则不足 |
| L3：双向往返 | 导入、修改、导出后，关键语义、引用和布局不丢失    | 尚未定义完整保证       |

例如，Figma 中可能存在复杂的 Auto Layout、组件属性、变量模式、嵌套实例覆盖、矢量路径和插件专有信息。

将这些内容转换成 iA-UI 的四层语义模型，不只是解析文件，还需要解决：

- 原始属性与目标语义之间的一对一、一对多或不可逆映射；
- 不可转换内容的保留策略；
- 导入前后视觉差异的衡量标准；
- 往返编辑时如何避免重复生成和信息丢失。

建议增加“兼容性矩阵 + 导入损失报告 + 不可逆操作提示”三项产品能力。

### 3.2 前端框架和组件库兼容性

文档提到 React + Tailwind、Vue 3、Svelte、React Native，以及 shadcn/ui、Ant Design、Material UI 等。

design.gemini.v0.0.3.md



问题在于，这些目标并不处于同一个抽象层级。

- React、Vue、Svelte 是不同的 UI 开发框架。
- Tailwind 是样式工具链。
- shadcn/ui 更偏向基于 React 生态的组件实现与分发方式。
- Ant Design、Material UI 各自具有组件 API、主题和状态语义。
- React Native 使用不同的布局、平台能力与渲染机制。

因此，不能只通过切换项目配置就假定同一份设计规格能够无损生成所有目标代码。

推荐采用以下结构：

统一 UI Spec / 语义 AST

业务、布局约束、组件语义、Token、交互和状态

目标适配器层

能力检测、组件映射、布局转换、主题映射、降级策略

Web 适配器

React / Vue / Svelte

Native 适配器

React Native 等

组件库适配器

shadcn/ui / Ant Design / MUI

设计系统适配器

Token / 主题 / 组件变体

适配器不应只是简单的代码生成模板，还应具有能力声明，例如某个目标组件是否支持特定变体、交互、无障碍属性和响应式行为。

当目标平台无法实现原始语义时，系统应明确告知用户，并提供替代方案，而不是静默地生成外观相似、行为不同的结果。

### 3.3 多端兼容性

文档采用“业务逻辑同构，物理排版独立”的多端设计思路，并支持 Desktop、Tablet、Mobile 画板。

design.gemini.v0.0.3.md



这比简单缩放桌面页面更加合理。不过，多端兼容不仅是断点和尺寸的问题，还包括：

- 输入方式：鼠标、键盘、触控、触控笔；
- 页面结构：导航栏、底部 Tab、侧边栏、抽屉；
- 操作习惯：悬停、长按、拖拽、返回手势；
- 平台差异：安全区、软键盘、系统字体、滚动与弹窗；
- 可访问性：焦点顺序、屏幕阅读器语义、缩放；
- 性能限制：低内存设备、弱网络、低端移动硬件。

此外，文档采用了纯流式布局的强约束策略。对于大多数业务 UI，这很有价值；但对于图表、地图、复杂数据可视化、自由曲线和重叠式视觉设计，可能需要受控的绝对定位、坐标系或专用画布。

因此建议将布局体系从“所有内容必须采用一种盒模型”调整为：

默认使用约束式流式布局，允许具有明确语义、明确边界和明确验证规则的特殊布局原语。

这样既能保障普通业务页面的可维护性，也不会牺牲特殊场景的表达能力。

### 3.4 编码 Agent 和 MCP 兼容性

文档希望通过标准 UI Spec 和 MCP 接口向 Cursor、Claude Code、Windsurf 等编码 Agent 交付设计规格。

design.gemini.v0.0.3.md



这有很高的实用价值，但必须区分三件事：

1. 协议兼容： 工具能够发现并调用接口。
2. 语义兼容： 不同编码 Agent 能正确理解同一份 UI Spec。
3. 结果兼容： 不同 Agent 生成的代码都满足同一组布局、交互和业务验收要求。

MCP 主要解决模型与工具之间的交互协议问题，并不会自动保证不同编码 Agent 对 UI Spec 的理解一致，更不会自动保证生成结果一致。

建议为每个外部 Agent 适配器定义统一接口：

- `get_spec`：读取完整或局部规格；
- `get_component_contract`：查询组件 API 和约束；
- `get_assets`：获取图标、字体及其他资产；
- `submit_implementation`：提交实现产物及元数据；
- `run_validation`：执行统一验收；
- `get_diagnostics`：获取结构化错误和修复建议。

以上是建议的产品接口，不是原文已经定义的 MCP 工具清单。

同时，平台需要一个与具体编码 Agent 无关的验收器。无论代码由哪个工具生成，都应接受同一套测试，避免将产品质量绑定在某个模型或某个编码工具上。

### 3.5 标准兼容性：使用标准，不等于完全符合标准

文档明确引入 W3C DTCG、JSON Schema、WCAG 2.1 和 MCP 等标准或协议。

design.gemini.v0.0.3.md



这种设计思路有助于减少自定义格式的生态壁垒，但需要注意标准的适用范围。

| 标准或协议       | 适合承担的职责          | 不能单独解决的问题                 |
| ----------- | ---------------- | ------------------------- |
| W3C DTCG    | 设计令牌的结构、交换和互操作   | 不能定义整个 UI 布局、业务动作和组件行为    |
| JSON Schema | 规格数据的结构校验        | 不能完整验证所有跨字段业务约束和渲染结果      |
| MCP         | 模型与工具之间的上下文及工具交互 | 不能保证生成代码正确，也不能替代权限与数据安全设计 |
| WCAG 2.1    | Web 内容无障碍的评估依据   | 不能仅通过静态检查证明整个应用符合无障碍要求    |

另一个需要澄清的地方是：文档要求全量推行 DTCG Token，但同时使用 CSS 变量、不同框架主题和组件库映射。这些之间需要一套明确的规范化规则，包括 Token 类型、引用解析、主题继承、单位转换和目标格式导出。

兼容性的关键不是列出多少标准，而是明确每项标准的边界、映射规则和一致性测试。

### 3.6 兼容性总结

| 维度             | 当前设计判断   | 主要风险                |
| -------------- | -------- | ------------------- |
| Figma 与设计资产导入  | 方向较好     | 语义转换与往返保真度未定义       |
| Web 框架与组件库     | 覆盖面广     | 组件语义、API 和布局行为差异    |
| 多端适配           | 基础思路合理   | 平台交互、特殊布局及设备差异      |
| 编码 Agent 与 MCP | 方向合理     | 协议通了，语义和结果仍可能不一致    |
| 开放标准           | 有较好的标准意识 | 标准间的映射与约束未形成完整契约    |
| 版本与第三方扩展       | 设计不足     | 规格升级、插件兼容、组件变更和迁移风险 |

我的判断是：兼容性设计理念较好，架构层面具备扩展潜力，但当前文档尚不足以证明实现后的互操作性。

## 四、创新性分析

判断创新性，需要区分三个层次：

1. 理念创新： 是否改变了用户完成任务的方式。
2. 架构创新： 是否形成了不同于现有产品的系统组织方式。
3. 技术创新： 是否提出了新的算法、协议或实现机制，并且能验证其效果。

iA-UI 在前两个层次具有一定辨识度；第三个层次目前主要是架构构想，尚未提供实现证据。

### 4.1 六项核心创新逐一分析

### 创新一：从画布中心转向意图中心

核心差异化

文档将自然语言意图、业务拓扑、设计约束和 Agent 决策作为主要工作流，而不是以手工图层操作为中心。

创新价值： 用户从“逐个画出页面”转向“描述产品、审查方案、修正结果”。这改变的是整个工作流程，而不仅是增加 AI 生成功能。

风险： 当 AI 对业务理解错误时，用户可能需要花更多时间纠正错误的全局设计。意图驱动不能取代必要的精细编辑能力。

文档将设计分为意图与逻辑、规范与约束、结构与流式布局、表现与图元四层，并通过稳定语义 ID 关联设计节点。

| 设计点                    | 创新程度判断  | 原因                       |
| ---------------------- | ------- | ------------------------ |
| 自然语言生成 UI              | 单独看创新有限 | 已经是 AI 设计产品的重要能力方向       |
| 多 Agent 分工             | 单独看创新有限 | 是一种常见的任务组织方式，效果取决于协调机制   |
| AI-DDL + 稳定语义 ID       | 较有潜力    | 如果形成统一且可验证的设计语义层，可支撑整个系统 |
| 画布操作反向提炼意图             | 较有潜力    | 把人工编辑转化为可复用的约束与决策        |
| Scope Guard + 依赖影响分析   | 较有潜力    | 有望解决 Agent 修改失控的问题       |
| UI Spec → 代码 → 验证 → 修复 | 组合价值较高  | 将设计与研发质量控制整合为连续工作流       |
| 工程级设计资产市场              | 生态层面的潜力 | 依赖资产可执行性、复用率和实际开发价值      |

最值得投入研发资源的不是 Multi-Agent Swarm 本身，而是三个相互依赖的核心能力：统一语义模型、可控增量修改、可验证的工程交付。

原因很简单：Agent 数量增加不一定提高质量，而这三项能力可以直接降低修改成本、减少语义损失，并让最终交付结果可以客观验收。

## 五、与现有产品的差异及竞争壁垒

文档提出的参考对象包括 Figma、Cursor、Claude Code、Storybook、Playwright、DTCG 等。

design.gemini.v0.0.3.md



这些参考对象说明产品设计有比较广的技术视野，但也带来一个问题：如果只是把这些工具的能力放进同一套工作台，是否足以形成竞争壁垒？

我的判断是：不足以。竞争壁垒需要来自这些能力之间形成的独特闭环。

下表是根据文档设计进行的概念层比较，不代表对各产品当前版本功能的全面实测。

| 对比维度     | 传统设计工作台     | AI 编码工具       | iA-UI 目标模式        |
| -------- | ----------- | ------------- | ----------------- |
| 主要输入     | 画布操作、组件和样式  | 自然语言、代码和项目上下文 | 产品意图、PRD、设计约束     |
| 核心产出     | 设计稿、组件和视觉资产 | 源代码及修改结果      | 语义化 UI Spec 和视觉设计 |
| 人工控制方式   | 直接编辑图层与属性   | 审查代码、提出修改要求   | 语义画布、局部约束与方案裁决    |
| 设计与代码的联系 | 依赖交接与工具链    | 以代码工程为中心      | 试图共享同一语义模型        |
| 质量验证     | 设计规范检查和人工评审 | 编译、测试和代码检查    | 设计规格、视觉、交互与工程验证   |
| 关键差异     | 视觉编辑效率      | 工程实现效率        | 跨越设计与实现的语义一致性     |

### 真正的竞争壁垒应如何形成？

建议把竞争壁垒设计为一个逐步增强的体系：

- 第一层：规格壁垒。 建立可靠的 UI Spec 与语义模型，使其能够覆盖常见业务 UI。
- 第二层：修改壁垒。 在多页面、多组件、多轮 AI 修改中保持局部可控、依赖明确、版本可追溯。
- 第三层：验证壁垒。 持续积累设计规格与实际代码之间的差异数据，提升诊断和修复能力。
- 第四层：资产壁垒。 沉淀经过真实工程验证的组件、页面模板、主题和交互资产。
- 第五层：生态壁垒。 让第三方组件库、设计师和编码 Agent 能够通过稳定接口参与生产流程。

其中，前三层是产品成立的前提，后两层才更有可能形成长期积累的优势。

## 六、文档内部的一致性与设计矛盾

除完整性和兼容性外，还有一些设计目标之间需要进一步协调的问题。

| 文档中的设计目标     | 潜在冲突                                  | 建议                       |
| ------------ | ------------------------------------- | ------------------------ |
| 所有布局采用流式盒模型  | 图表、自由画布、复杂重叠布局不一定适合纯流式布局              | 支持默认流式布局与受控特殊布局原语        |
| 背景画板绝对稳定     | 全局 Token 或共享组件变化可能要求多个画板同步更新          | 将背景只读与依赖传播区分开            |
| 毫秒级交互反馈      | 复杂 Agent 推理和多页面重新布局不可能始终在毫秒内完成        | 区分本地交互延迟、首个响应时间和完整任务完成时间 |
| 100% 保真交付    | 不同框架、浏览器、字体和设备存在渲染差异                  | 定义可测量的保真度指标及允许误差         |
| 多 Agent 自主协同 | 多个 Agent 可能对共享 Token、组件 API 和布局提出冲突修改 | 引入统一调度、依赖锁定、冲突裁决与原子提交    |
| AI 自愈直到完全达标  | 缺陷可能无法自动修复，修复可能反复引入新缺陷                | 设置迭代上限、失败退出、人工升级和回归检测    |
| 单一语义事实来源     | PRD、设计树、代码和运行状态可能同时发生变化               | 明确各类数据的权威来源、同步方向和冲突处理策略  |

其中最需要修改的是“100% 保真”和“完全达标”这类绝对化表述。

这些可以作为愿景，但不适合作为没有条件的工程承诺。建议改成明确的质量目标，例如：在指定浏览器、视口、字体、数据和组件版本下，通过规定的视觉、布局、交互及业务验收门槛。

这样更可测量，也更有利于后续实施和商业交付。

## 七、最优先的产品改进路线

我不建议继续大幅增加功能模块。文档目前的功能覆盖已经相当广，下一步更重要的是把核心能力变成可以验证、可以逐步交付的系统。

## 01

## 阶段一：确定统一语义规格

最高优先级

目标：让系统有统一的事实来源。

交付内容：

- 完整的 AI-DDL / UI Spec 规范与 JSON Schema。
- 节点、组件、Token、动作、状态机、Mock 数据的引用规则。
- 规格版本管理、迁移规则和第三方扩展机制。
- 明确哪些属性是视觉描述，哪些属性具有业务语义。

验收标准： 对同一份规格进行读取、修改、序列化和重新加载后，关键语义、引用和状态保持一致。

## 02

## 阶段二：实现可控的增量修改引擎

最高优先级

目标：让 AI 可以安全地修改已有设计。

交付内容：

- 稳定语义 ID 和 AST 差异计算。
- Patch 校验、版本冲突检测与原子提交。
- 组件实例与主组件的修改范围区分。
- 依赖影响分析、变更预览、撤销与重做。
- Agent 修改审计与人工干预优先策略。

验收标准： 对指定节点执行局部修改时，未授权的节点、引用和设计资产不会被意外修改；出现冲突时能够明确报告并恢复。

## 03

## 阶段三：打通最小工程交付闭环

最高优先级

目标：证明设计规格确实能够转化为可工作的代码。

交付内容：

- 选择一个 Web 框架和一套组件体系作为首个目标。
- 从 UI Spec 生成可运行的前端实现。
- 建立规格合法性、视觉、交互和工程四层验证。
- 实现结构化诊断、有限次自动修复和人工接管。
- 形成可重复运行的验收基准。

验收标准： 代表性页面能够通过预设的布局、交互和业务测试；失败时能够给出可定位的诊断，而非无限循环生成。

## 04

## 阶段四：扩展导入、跨端和多 Agent 能力

目标：从可验证的最小系统扩展到完整产品。

交付内容：

- Figma 导入与转换损失报告。
- 第二套组件体系及跨框架适配器。
- 多端布局、平台交互和无障碍验证。
- 更复杂的 Agent 并行任务、冲突裁决和恢复机制。

验收标准： 新增目标平台或组件体系时，无需重写核心语义模型，并能够使用同一套验收标准评估。

## 05

## 阶段五：建设资产生态与商业化能力

目标：形成可持续积累的设计资产。

交付内容：

- 可执行、可验证的工程级资产包。
- 组件依赖与许可证管理。
- 资产版本、兼容性、升级和回滚机制。
- 市场审核、授权、支付、退款与侵权处理。

验收标准： 第三方资产能够在声明的环境中安装、验证、升级和安全使用。

### 为什么不建议一开始就建设完整的 Multi-Agent Swarm？

因为如果 UI Spec 本身不稳定、补丁没有可靠事务语义、验证标准不完整，那么增加 Agent 数量只会增加协调成本。

更稳妥的路线是先用较少的 Agent 跑通一个确定性的流程，再根据实际任务瓶颈增加并行能力。

例如，最初只需要：

- 产品架构 Agent：生成业务结构和验收标准；
- UI 合成 Agent：生成结构化设计；
- 验证与修复 Agent：检查结果并输出有限次修复建议。

设计系统约束、补丁权限、规格校验和版本管理应尽量由确定性的底层服务执行，而不是依赖 Agent 自觉遵守规则。

## 八、最终评审结论

# iA-UI v0.0.3 综合评审

定性评审：基于产品设计文档，而非实际运行测试或竞品实测。

产品完整性

# 较高

功能蓝图覆盖广，工程闭环与契约仍需补全。

生态兼容性

# 有潜力

标准和适配思路合理，尚缺实际互操作验证。

创新性

# 较突出

创新主要在统一语义与跨设计、研发的闭环整合。

我的最终判断如下：

1\. 产品方向值得继续推进。 它不是单纯的 AI 绘图工具，而是试图构建一个能够将业务意图转化为工程级 UI 规格的设计与交付工作台。

2\. 当前最明显的短板是“目标定义得很完整，保障目标实现的规则还不够完整”。 文档定义了 Agent、画布、Token、Spec、MCP 和自愈等模块，但这些模块的输入输出契约、失败语义和一致性保证还需要更具体的定义。

3\. 核心创新应聚焦在语义层、增量修改和质量闭环。 这些能力决定产品能否比“AI 生成设计稿 + 编码 Agent 写代码”的简单组合更可靠。

4\. 暂时不宜以 100% 保真、全自动生产交付作为未经验证的承诺。 应先通过限定范围的端到端原型，测量生成成功率、修改副作用、视觉误差、交互测试通过率和修复成功率。

5\. 商业化市场应该后置。 在工程级资产真正可以跨项目复用、可靠升级和持续验证之前，过早建设完整的交易生态容易分散研发资源。

如果要对这份产品设计进行下一轮修订，我建议优先新增三个章节：《UI Spec 规范与演进契约》《增量修改与冲突一致性模型》《端到端验收标准与基准测试》。这三部分比继续增加功能清单更能提高产品设计的成熟度，也能直接降低后续开发过程中的架构返工风险。
